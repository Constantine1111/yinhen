## 改动 3：样式页预设卡片对齐

- 日期：2026-10-14
- 问题：4 张预设参考图比例不同（标准白框 1.26 / 拍立得 1.12 / 胶片 1.5 / 背景模糊 1.21），同行卡片高度不齐，标签位置错位
- 最终修复（Index.ets presetCard + presetsTab）：
  - 预设网格由 Flex 换行布局改为 Grid（columnsTemplate '1fr 1fr'，窄分栏单列时 '1fr'，columnsGap/rowsGap 10）
  - 卡片 height('100%') 填满 GridItem 单元格，行高自动取同行最高项
  - 卡片内部：图片顶部对齐 + Blank() 弹性占位 + 名称/描述底部对齐
  - 效果：同行卡片轮廓完全等高，图片顶边对齐、文字标签底边对齐
- 复盘：第一版尝试给 Flex 加 alignItems: Stretch 无效——该编辑误改到了别处的 Flex（品牌选择区，已还原），且 Flex 换行模式下 Stretch 本就不生效；第二版 Grid + height('100%') 中百分比高度在 Grid 自动行高下被解析为视口高度，导致卡片被撑到整个可视区（标签离图很远/文字下方大片空白）；第三版统一比例 + Cover 裁剪（用户否决：不裁剪参考图）
- 最终（第四版）方案：参考图保持原始比例零裁剪；Grid 监听 onAreaChange 获取实际网格宽度，按预设比例精确计算各图显示高度，卡片高度取同行两者最大值（headroom 常量 70 覆盖 padding/间距/标签）；卡片内部：图片顶部对齐 + Blank() 弹性占位 + 名称/描述底部对齐——同行卡片等高、名称行对齐、图与文字间距自动调节且不会过大
- 验证：构建成功，已部署真机（10.6.103.96:46255）

## 改动 6：尼康 Z / 索尼 α 型号字符自动识别

- 日期：2026-10-14
- 需求：手动输入或 EXIF 读入的型号中，尼康 Z 应显示为 ℤ、索尼 a 系列应显示为 α，并自动补全罗马数字标记
- 实现（渲染时转换，输入框保留原文，避免光标跳动）：
  - WatermarkModels.ets 新增 ROMAN_MARKS 常量 + normalizeRomanSuffix 函数（尾缀 ii/iii/iv 等合法罗马数字 → 大写 + 空格，排除单 I，幂等）
  - cleanModelText 增强：
    - 下划线分支提前处理（先于品牌转换），支持罗马字母尾缀（Z5_ii → ℤ5 II），last 先 trim
    - 尼康：Z→ℤ 后新增数字尾缀规则 `/^([ℤ]\d)([2-4])$/`（Z52 → ℤ5 II；Z30/Z50 尾 0 不误伤），再走 normalizeRomanSuffix（Z5ii → ℤ5 II）
    - 索尼：ILCE- → α；`/([aA])(?=\d)/g` → α（a7 → α7）；字母尾缀规则（a7r4 → α7R IV，字母 m/M 视为 Mark 省略：ILCE-7M4 → α7 IV；a7c2 → α7C II）；双数字尾缀 `/^(α\d)([2-4])$/`（a72 → α7 II；α99/α6400 等多位号不误伤）；再走 normalizeRomanSuffix（a7riv → α7r IV）
  - Index.ets 新增 camModelText() 方法（make 为空时按 brandPick/detectBrand 回退推断 NIKON/SONY），替换三处渲染点：camLine()（标准布局）、watermarkCanvas Span（分栏布局）、filmMainLine()（胶片布局）；输入框与 detectBrand 调用保留原文
- 验证：构建成功，已部署真机（10.6.103.96:46255）
- 备注 1：本次构建前发现 build-profile.json5 的 default 签名又被换回 E:/yinhen_key 发布材料导致真机安装 9568322，已再次在项目目录运行 `devecocli signature generate` 恢复调试签名（与改动 2 同法）；发布材料仍在 E:/yinhen_key 备用

- 备注 3（真机反馈补充）：手动输入的品牌名渲染时统一走 cleanMakeText（与 EXIF 加载一致）——camMakeText() 与 filmMainLine() 渲染点改为 `cleanMakeText(this.exif.make)`，输入 `nikon`/`NIKON`/`Nikon` 水印均显示 `Nikon`；输入框保留原文

## 改动 12：修复导出图片偶发全黑（照片区域黑、水印文字正常）

- 日期：2026-10-14
- 问题：导出的水印图偶发出现照片区域全黑（水印参数文字正常显示），单张/批量导出均可能触发，真机与模拟器均可复现，随机出现（同图多次导出有时正常有时黑）
- 根因（查官方 ComponentSnapshot 文档确认）：
  - `createFromBuilder` 的 `delay` 参数传了 0——文档明确"布局中使用了 Image 组件时需要指定延迟时间，以便系统解码图片资源"，默认值 300；传 0 强制不等待，偶发截图时 Image 的纹理尚未上传完成，照片区域渲染为黑
  - `checkImageStatus` 传了 false（默认值）——截图前不校验 Image 组件是否解码就绪，未就绪也照截
  - 附带发现：快照生成的 pixelMap 从不 release，批量导出多张时内存泄漏，加剧纹理上传失败概率
- 修复（Index.ets exportCurrent）：
  - `delay: 0 → 300`、`checkImageStatus: false → true`（Image 未就绪时抛 160001 异常而非产出黑图）
  - 快照失败自动重试：最多 3 次，间隔递增（200/500/800ms），新增 `sleep(ms)` helper
  - 保存完成后 `finally` 中 `pm.release()` 释放快照 pixelMap（修内存泄漏）
- 验证：arkts_check 通过，构建成功，已部署真机（10.6.103.96:46255）；待批量导出多张复测确认不再出现黑图

## 改动 21：导出保留 HDR（Ultra HDR 增益图二进制移植）

- 日期：2026-10-15
- 需求：HDR Vivid 照片加水印导出后，相册仍显示 HDR 效果，不再被压成纯 SDR
- 背景与方案演进：
  - 方案一（已弃用）：Picture API 多图对象（createPicture + setAuxiliaryPicture(GAINMAP) + packToFile(picture)）——实测 `packToFile(picture)` 静默丢弃增益图，输出无 iso21496/MPF，纯 SDR
  - 方案二（最终采用）：字节级二进制移植，不依赖 Picture 编码链路
- 实现（纯 ArkTS，ImageTools.ets）：
  - `readHdrJpegParts(uri)`：读取源文件字节，扫描 JPEG 段提取四部分——APP2[urn:iso:std:iso:ts:21496]（增益图元数据）、APP2[MPF]（多图索引，解析 TIFF IFD 0xB001/0xB002 → MPEntry）、APP8[ITUT35]（HDR Vivid 标记）、内嵌增益图 JPEG；按 MPF entry0.size 定位增益图，失败回落「主图 EOI 后」扫描；非 HDR 文件返回 undefined 走原 SDR 管线
  - `saveHdrToGallery(context, pm, parts)`：ImagePacker.packToData 打包加水印主图 → SOI 后插入三个源段 → 拼接增益图 → createAsset('jpg') 写入媒体库
  - **MPF 偏移修补（关键）**：规范中增益图偏移相对于 MPF TIFF 头（MP Endian 字段）起点而非文件头；输出偏移 = `primaryLen − (2 + isoSeg.length + 8)`（相对 OUT 自己的 TIFF 头位置）。曾误用源文件的偏移基准（实测 1664，即源文件 MPF TIFF 头位置）导致读者定位增益图提前约 1.6KB、落在主图熵数据中，媒体库扫不到 FFD8 判为 SDR——此为"结构正确但相册不识别"的根因
  - `verifyMpfOffsets(out, primaryLen)`：导出前以读者视角重解析输出缓冲，按修补后的 MPF 字段重新定位增益图并校验 FFD8，日志输出 selfcheck PASS/FAIL
- 修复导出过程预览异常（Index.ets previewArea）：可见预览与导出快照共用 @State canvasC，导出瞬间被换成导出布局导致预览区闪现异常画面；现 `saving || batchRunning` 时预览区显示 LoadingProgress + "正在导出..."，避免渲染中间态
- 约束：HDR 路径强制 JPEG 且仅源为 JPEG 双层结构时生效；PNG 导出与 SDR 源不受影响；源文件增益图后的非 MPF 引用尾部数据（疑似华为动态色调曲线，实测 826KB）未移植，实测不影响相册 HDR 显示
- 验证：真机 Pura X Max 实测通过——selfcheck PASS（tiffStart/e0size/e1off/FFD8 全对齐），相册确认导出照片显示 HDR Vivid
